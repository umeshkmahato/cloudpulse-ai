# ADR-0003: Terraform structure, state and cost gates
Status: Accepted (Phase 2)

## Decision
- 16 reusable modules under `infrastructure/terraform/modules`, thin per-environment roots (`dev`, `staging`, `prod`) that only wire modules and set values.
- Separate GCP project per environment (staging/prod projects do not exist yet; defaults are placeholders).
- State: local first (git-ignored); `bootstrap/` creates a versioned, non-public GCS bucket; environments then migrate via `terraform init -migrate-state`. State contains generated secrets, so the bucket is access-restricted (CMEK optional).
- Billable-while-idle resources (GKE, Cloud SQL, NAT, KMS) are boolean gates defaulting to false.
- Apply only through `scripts/tf-plan.sh` then `scripts/tf-apply.sh` (saved plan, typed confirmation, billable-resource refusal).
- GKE Autopilot chosen over Standard: no node management, per-pod billing, hardened defaults; trade-off is less node-level control.
- Secrets: containers in Terraform, values out-of-band; DB password generated by Terraform lands in state (documented risk; IAM DB auth is the follow-up).
- Auth to GCP from CI: Workload Identity Federation (module `iam`), no service-account keys.

## Consequences
Offline `fmt`/`validate` pass for all roots. `plan` needs credentials for the personal account, so no plan has been produced yet.
Staging/prod `main.tf` are generated copies of dev; a shared-root pattern (Terragrunt or a single parameterised root) is the evolution if drift becomes a problem.
